# 名称检查判定规则 — 参考

> 本 skill 的判定口径：脚本能判什么、什么算阻断、市场与检索状态如何表达、05 项交给模型做什么。
>
> **日常检查不需要读这一份。** 只在要改动判定逻辑时才按它核对：改 `scripts/` 下的脚本、
> 调整阻断项定义、改 02 项文案、改市场与检索状态的处理。

## A. 05 项：品牌 / 商标判定由调用方模型完成

脚本不内置品牌词表、不做品牌形态匹配、也不产出品牌相关的 `blockers`。
品牌识别（形近 / 内嵌 / 同形替换 / 跨语言别名 / 在先商标）只能由模型完成 ——
脚本给出**候选检查词**与**判定契约**，结论由模型补上。

### A.1 脚本侧给出什么

| 字段 | 含义 |
| --- | --- |
| `brandReview.delegated` | 恒为 `true` —— 品牌维度不由脚本处理 |
| `brandReview.targets[]` | 候选检查词。拉丁词：按分隔符切词 + 驼峰分段（`FreeChat`→`Free`/`Chat`）；中文：整段 + 2/3 字滑窗（`微信助手`→`微信助手`/`微信`/`信助`/`助手`） |
| `brandReview.contract` | 判定契约：`riskLevels` / `collisionForms` / `mustCheck` / `forbiddenClaims`。等级值恒为中文（**高 / 中 / 低**），字段名仅供回填、不进交付 |
| `trademarkAnalysis.overallRisk` | 占位名时 `'High'`，**其余一律 `null`** —— null 表示「待模型给出」 |
| `trademarkAnalysis.brandDimension` | 恒为 `'delegated'` |
| `trademarkAnalysis.screeningScope.brandCheckPerformed` | 恒为 `false` |
| `modelTasks[]` | 顶层数组，列出必须由模型完成的判定项 |

这些字段都只在 **JSON** 里。报告的 05 项小节只渲染素材（候选词 / 需核查尼斯类别 / 官方核查渠道 /
脚本侧的占用风险），**不渲染 `contract`** —— `mustCheck` / 结论格式 / 禁止声称项属写给调用方模型的
约定，渲染进报告只会被原样抄进交付文档。

### A.2 硬性约束

- **`overallRisk` 绝不能用 `'Low'` 冒充结论。** 没查过 ≠ 没问题。字段缺失消费方会自动走「未核实」，
  而 `'Low'` 会被读成「查过了，没问题」——方向必须失效到保守侧。
- **`blockers` 中不得出现品牌冲突项。** 脚本没有能力产出它。`spotify clone` 的 `blockers` 是空的，
  这是设计而非 bug —— 该结论由模型在 05 项给出后自行补充到 02 项。
- **报告不写成句的边界声明。** 05 项「未判定」只由**结构性状态**表达：05 项小节 status =
  `delegated`（icon 🧭、pill「未判定」）；给使用者的待办提示写 **stderr**
  （`[待办] 05 项商标与法务预检未判定…`）。
  成句声明会被调用方模型原样抄进交付文档，而交付文档里 05 项已由模型补上，抄进去即自相矛盾。
  参考节只留独特性评分；尼斯类别与官方核查渠道只在 05 项出现一次。
  - 调用方模型**不得再自由复述**这段边界（SKILL.md 交付第 7 条）；要交付的是 05 项的实际结论。
- **不得声称**：已按尼斯类别完成商标检索 / 已查询 USPTO、CNIPA、WIPO / 该名称无商标风险。
  这三条写在 `BRAND_REVIEW_CONTRACT.forbiddenClaims` 里，也在 SKILL.md 的红线里。

### A.3 模型必须给出的四样

风险等级（**高 / 中 / 低**）+ 命中的品牌与冲突形态 + 理由 + 2–4 个备选名。
**等级词一律中文**，与 `brandReview.contract.riskLevels` 的键一致；契约字段名仅供回填，
不写进交付文本。
冲突形态沿用 `BRAND_FORM_LABEL`：`exact` 独立使用 / `homoglyph` 同形字符替换 /
`embedded` 内嵌连写 / `typo` 形近变体。

### A.4 在线工具链接只放对话回复，不写进交付文档

固定一行（SKILL.md「交付给用户时的做法」第 6 条 + 红线第 8 条）：

> 想自己复看可视化报告的话，工具在这一页：[应用名称查重与命名政策检查 - 出海小纸条](https://www.appchecker.cn/name-checker)

- 标题写死即可，**不要为了写标题去抓取页面**。
- 之所以写成硬性要求：只作提示时模型时提时不提，交付不稳定。
- **它属于对话内容，不进交付文档、不进报告。** 文档正文应当只有结论，
  也不带任何工具自身的实现说明。

## B. 脚本可判定范围与阻断项定义

### B.1 `overallStatus` + `blockers` 是唯一真相源

「什么算阻断」只定义一次（见下表与 `blockersFor()`），退出码、报告 tone、01–05 项 status
全部由它派生。**改判定口径只改这一处。**
判读文案一律以 `report.mjs` 的 01–05 项为准；`appleVerdict` / `googleVerdict` 是单维度裁决，保留但非总结论。

| item | appliesTo | 触发条件 |
| --- | --- | --- |
| 01 | both | `charCount > 30` |
| 02 | **apple** | `hasExactMatch`（任一目标市场命中；Google Play 允许重名故不对 google 生效）。blocker 的 `detail` 会标明命中市场 |
| 03 | both | `foundBanned.length > 0 \|\| embeddedBanned.length > 0` |
| 04 | both | `hasEmoji` |
| 02 · 05 | both | `placeholderCheck.isBad` |

`overallStatus = blockersFor(platform).length > 0 ? 'Fail' : hasWarning(platform) ? 'Warning' : 'Pass'`

`hasWarning(p)` = `!allScansOk || (apple ? 任一市场有结果 : googleVerdict === 'Crowded / Allowed')`
（`allScansOk` = 全部目标市场都检索完成；只要有一个未完成就至少 Warning，未核实不能当「没问题」）

**⚠️ 范围声明。** `overallStatus` 只覆盖 `SCRIPT_AUDIT_SCOPE` 列的五项，不含品牌 / 商标。
`Pass` 的含义是「已判定的各项没问题」，不是「名称可用」。

⚠️ **报告文案里不得出现「脚本 / 模型」这类内部视角词。** 报告会被原样贴进交付文档，
内部视角词会让终端用户读到「这是一个自动化工具在说话」，且会被调用方模型复述。
现固定措辞：横幅 = 「未发现提审阻断项 / 存在 N 项优化建议 / 发现 N 项提审阻断」，
pill = 「待复核 / 建议优化 / 提审被拦截」，05 项状态与 pill = 「本项未判定 / 未判定」。

**⚠️ `appleVerdict` / `googleVerdict` 不是总结论。** 前者只看名称可锁定性（同名 / 占位名），
后者含政策违禁词但不含字符长度。对外一律只承诺 `overallStatus`。

`report.mjs` 保留「内部一致性告警」哨兵：`overallStatus` 与 01–05 项算出的结论不一致时报警，
防止口径漂移。**告警写 stderr，不进报告正文** —— 它含源文件名与字段名，属维护者诊断信息。

### B.2 05 项在报告里的状态是 `delegated`

`report.mjs` 的 `STATUS_LABEL` 多了一档 `delegated`（icon 🧭，文案「本项未判定」；
05 项的 pill 为「未判定」）。
它不参与 `fails` / `warns` 计数，因此不会把 tone 拉成 fail/warn ——
防「报告谎称完整」靠的是这个状态本身（🧭 本项未判定）与写往 stderr 的 `[待办]` 行，
不是横幅里的成句声明。

例外：名称为无效占位串时，05 项直接判 `fail`（`trademarkAnalysis.overallRisk = 'High'`），
因为「名称本身无效」是脚本能确定的事实，不需要模型介入。

### B.3 Apple 名称唯一性按本地化计，不是全局

02 项文案按以下口径表述：

- **Apple 官方原文**（《App Store Connect 帮助 · 添加新 App》FAQ「我想使用的 App 名称不可用，应该怎么办？」）：
  「针对 App 支持的每一种本地化语言，你可以分别提供一个 App 名称。」
  英文版同一句：`You can use an app name for one app per localization.`
- **含义**：唯一性的单位是**本地化（语言/地区）**，不是整个 App Store。
  某市场检出同名，只说明该市场对应的本地化已被占用，未命中的本地化不受影响。
  02 项文案一律按此表述，并分别写明命中市场与未命中市场的可用性。
- **实测旁证**：US 区 iTunes API 192 条结果中，字面完全同名 `Calculator` 有 2 款
  （Apple 自家 `com.apple.calculator` 与 The App Tower），另有 18 款用 Unicode 变体
  （`Calculator₊` `Calculator‰` `Calculator⁼` `Calculator·`）绕过同名校验。

## C. 商店检索与状态位

### C.0 市场（检索地区）是必填的，多市场结果不可合并

- **没有默认市场。** `--country`（别名 `-c` / `--market`）不传直接抛错、退出码 2。
  理由：商店检索结果本身就是分市场返回的（Apple 走 `country=xx` 店铺、Google 走 `gl=xx`），
  同一名称在不同市场的占用情况可以完全不同 —— 实测 `Calculator` 在 US 有完全同名（判 `Fail`），
  在 HK 却没有。替用户填默认值 = 把某个市场的结论冒充成用户市场的结论。
- **支持多市场**：`-c us,hk,jp`，逗号/斜杠/空格分隔，也可重复传 `-c us -c hk`。去重后按顺序逐个检索。
  校验只要求两位字母码（`/^[a-z]{2}$/`），所以 `nl` / `th` 这类没进「常用市场」的地区也能传。
- **逐市场各调一次 `scanStore`**，不要把市场参数并成一个请求。
  `scanStore({ name, platform, market })` 的 `market` 亦是必填，缺失抛错。
- **`scanStore` 返回的顶层 `ok` / `reason` 必须透出去。** 上层（`engine.mjs` 构造 `marketScans` 时）
  读不到就会把所有市场误判成 `network_failed`。
  `engine.mjs` 侧另做了 `s.ok ?? s.storeScan?.ok ?? false` 的兜底，任一缺失都按「未完成」处理
  （失效到保守侧）。
- **结果行内的 `country` 写真实市场码。** 请求本身带 `gl=xx`，结果就是该店铺的结果，
  标成 `"GLOBAL"` 后多市场结果无法区分。
- **竞争拥挤度看单市场最大值，不看并集。** `maxMarketMatchCount = max(各市场 matches.length)`。
  用并集判阈值会被市场数放大（5 个市场各 1 条 → 并集 5 条 → 误判 `High`）。
- **结论必须落到市场粒度。** 报告按市场分节出表（多市场时先给一张汇总表）；
  02 项逐市场陈述（`buildMarketBreakdown`）。「US 没有同名」不得写成「没有同名」。

### C.1 状态位

- **检索未完成时禁止出具通过结论。** 检索函数的失败路径不得返回空数组了事：
  `searchGooglePlay` 返回 `{ apps, ok, reason }`，`reason` = `network_failed`（HTTP 失败 / 抛出）
  或 `parser_failed`（Google 换了混淆类名：页面里有 `details?id=` 链接却解析出 0 个应用）。
  iTunes 侧：`!res.ok` → network_failed；返回体不是 `results` 数组 → parser_failed；
  **`results: []` 属正常「查到了但没有」，`ok` 仍为 true**。
- 输出字段 `storeSearchStatus` + `storeSearchNote` + 逐市场的 `marketScans[].status`。取值：
  - `completed` —— **所有**目标市场都查完了（多市场时缺一个就不算）
  - `partial` —— 多市场下**只查完一部分**。此时逐市场结论仍可用，但只能说「已查完的市场没有同名」，
    未完成的市场一律标未核实。02 项 pill 显示「部分市场未完成」，横幅与 `storeSearchNote` 都写明哪些市场未完成
  - `network_failed` / `parser_failed` —— 全都没查到
  - `skipped` —— 主动离线（`--offline`），所有市场都记 skipped
- 未完成时：`appleVerdict` 不判 `Close Matches`，`googleVerdict` 不判 `Crowded`；`overallStatus` 至少为 Warning
  （`hasWarning` 里「有市场没跑完」是第一条件）；报告 02 项走 warn 分支、
  检索卡改未完成态、横幅追加未核实提示。
- **判定写的是 `result.storeSearchStatus !== 'completed'`**，所以字段缺失
  会走「未核实」而不是「无冲突」——这是刻意的失效方向，别改成默认通过。
- **`--offline` 记 `skipped`**，不伪装成 `network_failed`。主动不查 ≠ 查失败，
  报告措辞必须区分，否则等于把「用户没查」说成「查不出来」。
